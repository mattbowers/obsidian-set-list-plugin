# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a functionally complete Obsidian community plugin (v1.0.0) implementing the design in `Obsidian Set List Plugin.md` — read that file for the original product concepts (Song, Set List, Edit view, Stage view).

**Known issue, not yet fixed:** a PDF song shown in Stage view sometimes renders with the wrong layout at first (e.g. a two-page-spread PDF shows only one page), then self-corrects after roughly 30 seconds with no user interaction. Investigated at length in one session without landing a fix; breadcrumbs for whoever picks it up next:
- Stage view renders PDFs via `renderSong.ts`'s synthetic `![[file.pdf]]` embed through `MarkdownRenderer.render()` — a fundamentally different, more constrained Obsidian component (`isEmbed: true`, default `height: "page"` i.e. capped to roughly one page unless a `#height=N` pixel value is given in the embed link) than opening a PDF directly as its own tab (Obsidian's dedicated `PdfView`, no such cap). Confirmed by extracting and reading Obsidian's own compiled `obsidian.asar` (`npx asar extract`, then grep) — both `chord-sheets-mb`'s and Obsidian's own compiled sources are legitimate, high-value places to look when static analysis of this repo alone doesn't explain a symptom.
- Devtools comparison: Obsidian's internal `.pdf-container` (the PDF viewer's own scroll container, nested inside `.pdf-embed`) computed to a real 0px height in Stage view despite having real page content already inside it (children `position: absolute`, no inline height set) and a real non-zero-height parent to inherit from — not the kind of break a normal CSS percentage-height chain produces. A real dedicated PDF tab, even opened cold, shows the correct layout instantly — ruling out this being generic slow PDF/page-count parsing.
- Three targeted fixes were tried and reverted after live verification:
  1. Giving `.set-list-stage-content`/`.set-list-song-area`/`.set-list-song-container` explicit `height: 100%` immediately/permanently. This measurably fixed `.markdown-preview-view` down through `.set-list-stage-view` inheriting a real height — but, importantly, it made the PDF issue *worse*: the ~30s self-correction stopped happening at all, leaving it stuck in the wrong layout indefinitely. This is itself a useful clue (see below), not just a failed fix.
  2. Deliberately nudging the rendered container's own size ~2s after render, to wake a `ResizeObserver` confirmed to exist in Obsidian's PDF viewer (`pdf.viewer.min.mjs`, debounced 200ms). No effect either way.
  3. A "deferred settle" compromise: leave `.set-list-song-container` unsized at creation, then add an `.is-settled` class (`height: 100%`) ~500ms later, for PDFs only — aiming to give the PDF viewer's `ResizeObserver` one deliberate, early, real size change to react to (rather than either a permanently-static value, per fix 1, or nothing until the natural ~30s trigger). Also no visible improvement.
- What fix 1 tells us: before any of these changes, `.set-list-stage-content` only had `min-height: 100%` (not `height`), so its actual computed height could still shift slightly during the page's normal settling (workspace layout passes, sidebar state, font loading, etc.) before landing on its final value — and that natural "unsettled → settles" transition is almost certainly what the PDF viewer's `ResizeObserver` was picking up as its trigger. Locking the chain rigid from the very first paint removed every future size change for it to react to. Fix 3 tried to reproduce that transition deliberately and quickly instead of waiting on it — it didn't work, so either the timing was still wrong, or the actually-observed element is something other than `.set-list-song-container` (possibly higher up the chain, or something not touched by these three attempts at all).
- Next step, not yet done: needs live JS debugging rather than more static guessing — in Obsidian's devtools, right-click `.pdf-container` in the Elements panel → Break on → Attribute modifications (or Subtree modifications, or try the parent), then wait for the ~30s self-correction to hit the breakpoint and read the real call stack. That would show definitively which element's resize is the actual trigger and what code reacts to it, instead of continuing to guess.

## Commands

- `npm run dev` — esbuild watch mode, rebuilds `main.js` on change
- `npm run build` — type-check (`tsc -noEmit`) then production esbuild bundle
- `npm run check` — type-check only
- `npm test` — run the vitest suite (pure-logic tests only; view/rendering/gesture wiring is verified manually in Obsidian, not unit tested)

### Local dev loop

Symlink this repo into a test vault's plugin folder, e.g. `<vault>/.obsidian/plugins/obsidian-set-list-plugin`, and install the community `hot-reload` plugin in that vault — it picks up a fresh `main.js` after each build automatically. Sample song/set-list files for manual testing live outside this repo at `/Users/matthew/Documents/Vaults/Testbed`; the plugin also renders through the vault's separately-installed `chord-sheets-mb` plugin for some songs, which this plugin has no code dependency on but which its Stage/Edit views' DOM structure (`.markdown-reading-view` / `.markdown-preview-view` / `.markdown-rendered`) must stay compatible with for correct visual rendering.

Each build bakes a `__BUILD_TIME__` timestamp (via esbuild `define`) into the bundle; both views render a small "vX.Y.Z · built HH:MM:SS" badge (`src/ui/buildBadge.ts`) so you can visually confirm a rebuild reached a device (useful on mobile/tablet, where devtools aren't handy).

## Architecture

- `src/main.ts` — plugin entry: registers the two views, a command palette entry for every toolbar/gesture action in both views (gated by `checkCallback` — file-type-only checks for switch-view/source-mode/new-set-list, plus active-view-type and, for the selected-song actions, `SetListEditView.hasValidSelection()`/`getSelectedFile()`/`getBandName()` checks — so a command is only listed when it would actually do something), a "New set list" ribbon icon (creates a note with `type: SetList` frontmatter via `FileManager.getNewFileParent` — the same folder-placement logic Obsidian's own "New note" uses — and opens it directly in Edit view), and installs `sidebarSwipeGuard`. "Switch to stage view" routes through the active `SetListEditView.enterStageView()` when there is one (selected song, else first song), rather than always starting from scratch, so it matches that view's toolbar button exactly.
- `src/setlist/` — pure data model, no Obsidian view/UI code:
  - `types.ts` — `SongEntry` / `TextEntry` / `SetListEntry` union, `ParsedSetList { preamble, entries }`.
  - `parser.ts` — `isSetListFile` (frontmatter `type: SetList`, case/whitespace-tolerant), `getBandName` (trimmed `band` frontmatter value, or `null`), `parseSetList` (splits frontmatter as an untouched preamble, classifies each body line as song/text by cross-referencing `CachedMetadata.links[].position.start.line`, resolves links via an injected callback).
  - `serializer.ts` — `serializeSetList`, the exact inverse of the parser (preamble + entries' raw lines).
  - `mutations.ts` — pure `addSong` / `removeSong` / `replaceSong` / `reorder` / `appendEntries` (bulk-append, e.g. clipboard import) over a `ParsedSetList`.
  - `persist.ts` — writes a mutated `ParsedSetList` back via `Vault.process`.
  - `navigation.ts` — `findFirstSongIndex` / `findNextSongIndex` / `findPrevSongIndex`, skipping non-song entries.
  - `tagging.ts` — `sanitizeTag` (slugifies an arbitrary string, e.g. a frontmatter property's value, into a valid Obsidian tag) and `addTagToAllSongs` (adds a tag to every resolved song file's frontmatter via `FileManager.processFrontMatter`, deduping by path first and skipping a file that already has the tag case-insensitively).
  - `textNormalize.ts` — `normalizeForMatch` (lowercases, spells out `&` as "and", drops apostrophes/quotes outright rather than turning them into a space so "don't" → "dont", then turns any other punctuation/symbol run into a single space). Split out from `songMatch.ts` specifically so it has no `obsidian` value import and stays unit-testable — `songMatch.ts` imports `prepareFuzzySearch` as a value, which only exists inside the real Obsidian runtime, not the types-only `obsidian` npm package these tests run against, so importing it at all breaks a test file.
  - `songMatch.ts` — `findBestSongMatch` (best-effort match of an arbitrary line of text to a vault song file: exact match wins outright, else the best-scoring `prepareFuzzySearch` match, else `null`; both sides go through `normalizeForMatch` first, since otherwise a query character absent from the target — e.g. an apostrophe the file name doesn't have — makes the whole fuzzy search fail outright, not just score low. Candidates exclude other set list notes, same as `SongPickerModal`.) Not unit tested itself, for the reason above.
- `src/views/`:
  - `viewTypes.ts` — the two view-type string constants (kept separate to avoid a circular import between the two view files).
  - `BaseSetListView.ts` — shared `FileView` base: parses on load, re-parses on `metadataCache.on("changed", ...)` (not `vault.on("modify")` — the latter fires before the metadata cache re-indexes, which caused a stale-render bug).
  - `SetListEditView.ts` — toolbar (add/remove/reorder via drag-and-drop/enter stage view/drop to raw markdown Source Mode, the escape hatch now that Edit view opens automatically — see `main.ts`; also paste-songs-from-clipboard: each non-blank clipboard line becomes a song row via `findBestSongMatch`, or a plain text row if nothing matched, appended via `appendEntries`, so an unmatched line stays visible to fix by hand rather than being silently dropped; and its opposite, copy-to-clipboard: every entry becomes one plain-text line — a song's `displayText` (no wikilink markup) for song rows, the raw line for text rows, blank text rows dropped — so the result round-trips back through paste). "Add song" inserts the new song right after the current selection (end of the list if nothing's selected), and the newly-added song becomes the selection — so with the picker staying open across successive adds, each pick lands after the previous one instead of every pick reinserting right after the original selection and ending up in reverse order. "Direct open song" (`openDirectSongPicker`) opens the same `SongPickerModal` but jumps straight into Stage view showing whatever's picked, via `enterStageView(file)`'s new optional ad hoc-file argument — for a request or filler song mid-set that shouldn't become a permanent part of the set list. A lock button (leftmost in the toolbar, accent-colored via `.set-list-lock-button`, `locked` defaulting to `true`) gates every action that writes to the note or a song file — add/replace/remove/reorder, tag-all-with-band, paste/copy — leaving only Enter stage view, Direct open song, and Open song as new tab (plus row click-to-select and double-click-to-enter-stage-view, since those two allowed actions need a selection) available while locked; each gated method re-checks `this.locked` itself (not just the toolbar's `disabled` attribute), and `main.ts`'s matching commands re-check `view.isLocked()` in their own `checkCallback`s, including `open-source-mode` even though that command isn't tied to a specific view method. `.set-list-toolbar.is-unlocked` swaps in an accent-tinted background (`color-mix`) so the "editing is live" state reads as visually distinct from the default locked/read-only one. Reordering itself stays enforced purely in JS, not via the row's `draggable` attribute: a song row is *always* `draggable="true"`, even while locked, because mobile's native touch-based drag-and-drop only reliably engages when an element is draggable from its very first render — toggling the attribute later (e.g. right after tapping unlock) doesn't reliably register as drag-eligible on touch the way it does with a mouse, which broke drag-reorder on mobile specifically (desktop was unaffected) the first time locking was tied to the attribute. The lock is enforced instead by calling `evt.preventDefault()` in the row's own `dragstart` handler when locked (skipping `dragFromIndex`/`dragRowLayout` setup entirely), with `handleDrop`'s own `if (this.locked) return;` as a second line of defense. The `.set-list-toolbar` sticky container is a column: a `.set-list-toolbar-header` line (song count, plus the set list's own `band` frontmatter value via `getBandName` when present, e.g. "The Wow Band · 13 songs") above a `.set-list-toolbar-buttons` row holding the actual icon buttons (song actions left, `.set-list-toolbar-group-right` set-list-level actions right). A song row shows a smaller, dimmer metadata line under its title — `artist`/`key`/`tempo` read from that *song file's own* frontmatter (`getSongMetadataLine`, not the set list's), joined with " · ", any subset present; omitted entirely if the song has none of the three. Dragging slides in-between rows out of the way via CSS `transform: translateY(...)` sized to the dragged row's own height. `dragover`/`drop` are handled once at the row-list container, not per-row: per-row handlers were tried first and broke, because shifting a row via `transform` moves it out from under the cursor mid-drag, which retargets/cancels the native drag-and-drop hit-test and made drops silently no-op. The fix snapshots every row's midpoint Y (`dragRowLayout`) once at `dragstart`, before any shuffling starts, and all later insertion-point math (both the shuffle animation and the final `reorder()` call) is computed from `event.clientY` against that frozen snapshot rather than from live element positions or `event.target`.
  - `SetListStageView.ts` — persistent DOM scaffold (built once in `initScaffold`, re-rendered content-only on navigation) layering a gesture-capture overlay over the rendered song; `currentIndex` persisted via `getState`/`setState`. `setState`'s optional `adHocPath` (resolved to a `TFile` as `adHocFile`, round-tripped back out through `getState`) is how Edit view's "Direct open song" hands off a song that isn't necessarily part of the set list — `render()` shows it in place of `parsed.entries[currentIndex]` without touching `parsed` or writing to the note (no visual indicator that it's ad hoc — deliberately plain), framed as if it were inserted right before `currentIndex` in the real set list: `goToNext` reveals the song actually at `currentIndex` (unchanged) rather than skipping past it, while `goToPrev` goes to whatever came before `currentIndex` — both then clear `adHocFile` so navigation continues normally from there. `currentIndex` itself comes from `enterStageView`'s usual current-selection-or-first-song default, computed alongside the ad hoc file, not from the ad hoc pick itself, and `lastStageIndexByFile` is left untouched while an ad hoc song is showing, so returning to Edit view still highlights the real current song.
- `src/render/renderSong.ts` — renders a song file through Obsidian's real `MarkdownRenderer.render` pipeline (so third-party post-processors like `chord-sheets-mb` run normally); non-md files (e.g. PDFs) render via a synthetic `![[path]]` embed rather than a hand-rolled viewer. Markdown songs only, a `.set-list-song-title` div (the file's basename) is prepended ahead of the rendered content — skipped for PDFs, whose own content already shows a title. Part of the normal scrolling content (not a sticky header), so it scrolls away with the rest of the song.
- `src/gestures/`:
  - `StageGestureController.ts` — framework-agnostic pointer-event state machine for Stage view: a horizontal swipe anywhere on the overlay navigates prev/next (left drags the next song into view, right drags the previous one), a stationary long-press exits to Edit view. A swipe requires enough horizontal travel (`swipeMinDistance`) and stays mostly horizontal (`swipeMaxVerticalRatio`), so a vertical scroll or diagonal drag doesn't misfire. Classification happens on `pointerup`; `pointercancel` is also classified rather than dropped — using position from the last real `onPointerMove` sample (not the cancel event's own, often stale/start-like, coordinates) but the cancel's own timestamp — this specifically handles Obsidian's own edge-swipe gesture recognizer stealing a touch near the screen edge (which fires a cancel, not an up) for both an in-progress swipe and a stationary long-press, without misfiring on ordinary vertical scrolls that also get resolved via a cancel.
  - `sidebarSwipeGuard.ts` — wraps `app.workspace.trigger` to swallow the internal `"swipe"` event (Obsidian's own mechanism for opening/closing sidebars on mobile) while Stage view is active. This is a separate, lower-level mitigation from `StageGestureController` and exists because Obsidian's sidebar-swipe detection isn't a normal bubbling DOM listener `stopPropagation()` can intercept.
- `src/ui/`:
  - `SongPickerModal.ts` — `FuzzySuggestModal<TFile>` over markdown + PDF vault files, excluding other set list notes (`isSetListFile`); `getItems()` sorts them alphabetically by basename before any fuzzy-search re-ranking, so the unfiltered/empty-query listing (and every call site: add, replace, direct-open) shows songs A→Z rather than vault order. A `Setting`/toggle inserted above the results (via `resultContainerEl.before(...)`, since `Setting`'s constructor always appends) filters to songs tagged with the set list's band tag; on by default, disabled (nothing to filter by) when the set list has no `band` frontmatter. `getItems()` is re-filtered live and re-run by dispatching a synthetic `input` event on `inputEl` — `FuzzySuggestModal` has no public API to force a suggestions refresh otherwise. `selectSuggestion` is overridden (not just `onChooseItem`) because the base `SuggestModal` closes the modal right after choosing an item; a `closeOnChoose` constructor flag picks between the two call sites' needs — the add flow (`false`) clears/refocuses `inputEl` and stays open so several songs can be picked in quick succession (the modal's own top-right close button is how the user leaves), while the replace flow (`true`) closes immediately, since there's only one slot to fill. `includedPaths` (dimmed = already in the set list) is a mutable copy seeded from the constructor, grown as songs are picked in this same session.
  - `buildBadge.ts` — the build-time verification badge described above.
- `src/__tests__/` — vitest fixtures for the parser/serializer round-trip, mutations, navigation skip-logic, and gesture classification, modeled on real Testbed sample-file patterns (aliased links, `.pdf` links, unresolved links, interleaved text/blank rows, frontmatter casing).

## Design notes worth preserving

- Views are reachable via the two explicit commands (`checkCallback` gated on `isSetListFile`), plus `main.ts`'s `file-open` handler auto-switches a set-list note into Edit view every time it's opened as a plain `MarkdownView` — normal (non-set-list) notes are never touched, and a note the user has explicitly put into Source Mode (`state.mode === "source" && state.source === true`) is left alone rather than force-switched. `SetListEditView`'s "Source mode" button is the escape hatch back to raw markdown; it sets that same `source: true` state so the note stays put on next open instead of immediately auto-switching back. The `setViewState` call in the `file-open` handler races Obsidian's own still-in-flight file-opening pipeline, which can silently revert it back to `markdown` right after it resolves — `maybeOpenEditView` re-checks the resulting view type and retries on the next `requestAnimationFrame` (up to `MAX_OPEN_EDIT_VIEW_ATTEMPTS`) rather than trusting a single fixed delay. Getting back to Edit view from Source mode via Obsidian's own core "Reading view" toggle button doesn't fire `file-open` (it flips `MarkdownView`'s mode within the same leaf), so `main.ts` also listens for the workspace's `layout-change` event and re-runs `maybeOpenEditView` — its existing `state.mode === "source"` check naturally lets this through once the mode is no longer literally `"source"`.
- Tag-all-songs-with-band, paste-songs-from-clipboard, and copy-to-clipboard are desktop-only, off-stage workflows — their toolbar buttons (`Platform.isDesktop` in `SetListEditView.render`) and commands (`Platform.isDesktop` in each `checkCallback` in `main.ts`) are both hidden on mobile, kept in sync with each other the same way every other toolbar action's command is gated on the action actually being available.
- `parseSetList`/`resolveLink` take an injected callback rather than calling `metadataCache.getFirstLinkpathDest` directly, keeping the whole `setlist/` module testable without a real Obsidian runtime (the `obsidian` npm package is types-only, so `import type { TFile } from "obsidian"` is safe in tests).
- Stage view's gesture overlay intentionally intercepts every pointer event over the rendered song (so a mistimed tap during a performance can't hit a real link) — only vertical scroll passes through, via CSS `touch-action: pan-y`, not JS.
- Stage view's `.set-list-song-container`/`markdown-reading-view` wrapper (see `renderSong.ts` DOM structure above) deliberately carries no padding of its own — Obsidian's/the active theme's own CSS already applies file-margin padding to `.markdown-reading-view`/`.markdown-preview-view` by class name, matching regardless of DOM nesting depth, so it applies to this manually-built structure too even though it isn't the real `MarkdownPreviewView`. An earlier `padding: var(--size-4-4)` on `.set-list-song-container` stacked on top of that, showing up as extra margin versus opening the same note directly outside Stage view. `.set-list-stage-view` (applied straight to the view's own `.view-content`, i.e. `contentEl`) needs its own `padding: 0 !important` for the same reason, mirroring `.set-list-edit-view`'s existing override just below it — a real note's reading view cancels Obsidian's default `.view-content` padding and manages its own margins instead, so leaving that default padding in place here stacks yet another layer on top. The `!important` is load-bearing here (confirmed via devtools): a plain override left `.view-content` at its default `12px 12px 12px 32px` padding regardless — on mobile, Obsidian reserves that oversized left inset for its floating sidebar-toggle button, applied with enough specificity/priority that only `!important` reliably cancels it.
